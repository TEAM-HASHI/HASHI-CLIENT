# 컬렉션 API 연동 (HASHI-224 / HASHI-238 / HASHI-239)

## 범위와 PR 구조

- 기반은 #226 OpenAPI 타입과 컬렉션 UI·인증 PR #221이 병합된 최신 `develop`이다.
- 조회 3개 → 생성·수정 2개 → 식당 관리·컬렉션 삭제 4개의 순서로 PR을 쌓는다.
- 첫 조회 PR #240의 base는 `develop`이며, #243 생성·수정 → #244 식당 관리 순으로 쌓는다.

| PR                    | 브랜치                                     | base                                 |
| --------------------- | ------------------------------------------ | ------------------------------------ |
| 조회                  | `feat/HASHI-224-collection-read-api`       | `develop`                            |
| 생성·수정             | `feat/HASHI-238-collection-form-api`       | `feat/HASHI-224-collection-read-api` |
| 식당 관리·컬렉션 삭제 | `feat/HASHI-239-collection-management-api` | `feat/HASHI-238-collection-form-api` |

Jira는 조회 `HASHI-224`, 생성·수정 `HASHI-238`, 식당 관리·컬렉션 삭제 `HASHI-239`로 분리한다.
브랜치명·커밋 메시지·PR 제목·본문은 각 Jira 번호를 사용한다.
Stack은 develop → #240 → #243 → #244이다. 출발 브랜치 변경으로 닫힌 #241·#242는 각각 #243·#244가 대체한다.

각 PR 범위에 속하는 파일만 커밋한다. 원래 작업 공간의 기존 API 브랜치와 파일은 보존한다.

- 식당 상세 저장 버튼, 지도 핀 및 식당별 저장 여부·저장 수 API 연결은 제외한다.
- 커밋·푸시·실서버 데이터 변경은 사용자 승인 전 실행하지 않는다.

## Data Dependencies

### 조회 계약

| 데이터                | Endpoint                                             | 입력                                                 | 방식              |
| --------------------- | ---------------------------------------------------- | ---------------------------------------------------- | ----------------- |
| 내 컬렉션·대상 목록   | `GET /api/v1/collections`                            | `restaurantId?`, 숫자 `cursor?`, `size?`             | infinite query    |
| 상세 헤더·수정 초기값 | `GET /api/v1/collections/{collectionId}`             | 양의 안전한 정수 ID                                  | conditional query |
| 저장 식당 목록        | `GET /api/v1/collections/{collectionId}/restaurants` | ID, `sort?`, `placeType?`, 문자열 `cursor?`, `size?` | infinite query    |

- endpoint는 기존 `shared/api/request`에 요청·인증·오류 처리를 위임하고 `AbortSignal`을 전달한다.
- 요청·응답 타입은 owning app의 generated OpenAPI에서 파생한다.
- query key는 `collectionQueryKeys`를 사용한다. cursor는 key가 아니라 `pageParam`으로 관리한다.
- UI의 `reviews`는 서버의 `review`, `all`은 `placeType` 생략으로 변환한다.
- 상세·식당 조회는 유효한 ID가 있을 때 실행한다. 내 목록은 소비자가 인증 준비 전 `params=null`을 전달한다.
- 비활성 인수로 수동 refetch해도 endpoint를 호출하지 않는다.
- `hasNext=false`면 추가 조회를 끝낸다. 누락된 페이지 정보·목록·잘못된 cursor는 빈 목록 성공으로 바꾸지 않는다.
- 실패를 local query state로 전달하며 query retry는 공통 정책을 따른다. 추가 페이지 실패 시 기존 페이지를 보존한다.
- `totalCount`와 `savedCount`는 서버 값을 보존한다. 상세 상단 개수는 저장 식당 응답의 필터별 `totalCount`를 사용한다.

### 화면 모델 경계

- summary에는 설명·생성일·전체 식당 관계가 없다. 기존 목 `SavedCollection`로 가장하지 않는다.
- ID를 검증해 화면용 문자열로 변환한다. 없는 ID·평점·지역·분류를 임의 생성하지 않는다.
- 공개 여부는 알려진 `visibility`만 변환한다. 알 수 없는 값은 공개나 비공개로 단정하지 않는다.
- `cover.imageUrls`는 기존 세 이미지 슬롯으로 변환한다. 빈 칸은 fallback용 `null`이다.
- `thumbnailUrl`과 `thumbnailImage`를 함께 보존한다. 최종 표시 시 공통 미디어 선택 계약을 적용한다.
- 목록 행은 표시용 필드만 받아 summary·식당 조회 모델을 직접 표시할 수 있다.
  누락된 평점·저장 수·공개 여부를 0이나 비공개로 대체하지 않으며, 알려지지 않은 커버 색상은 기존 이미지 fallback을 사용한다.
- 제품 화면은 API query·mutation을 사용한다. 지도/fixture public props는 기존 계약을 유지한다.
- #221의 `getAuthSessionVersion`·`subscribeAuthSession`을 재사용한다. 컬렉션 전용 인증·토큰 저장소는 만들지 않는다.
- 목록·상세·저장 식당·이동 사전 조회 key는 세션 버전을 포함한다. 계정 변경 시 다른 캐시를 조회하고 이전 요청의 늦은 응답은 반영하지 않는다. 토큰 재발급만으로는 key를 변경하지 않는다.
- 생성·수정·저장·해제·이동·삭제는 시작한 세션을 보존한다. 요청 전후와 비동기 캐시 취소 이후 세션을 확인하며 이전 세션 응답은 현재 캐시·오류 안내·화면 복귀를 실행하지 않는다.
- 계정 변경 시 생성 입력·편집 선택·관리/공유창을 초기화하고 이전 계정의 생성 복귀 상태를 재사용하지 않는다. 서버에 이미 전달된 쓰기를 취소·롤백한다고 보장하지 않는다.
- 실제 조회 데이터와 기존 목 mutation을 섞어 저장·이동·삭제가 성공한 것처럼 표시하지 않는다.

### 조회 화면 연결 상태

- `SavedQueryPage`는 조회 3개를 실제 query hook·화면 모델에 연결한다. 목 Provider를 사용하지 않는다.
- 기존 화면과 `SavedPageLayout`을 공유해 고정 헤더·내부 스크롤을 유지한다.
  추가 조회의 IntersectionObserver root도 이 내부 스크롤 영역이다.
- 초기 loading·오류 재시도·빈 목록과 추가 페이지 실패를 구분한다.
  추가 조회 실패 시 기존 항목을 유지하고 자동 추가 요청을 멈춘 뒤 같은 cursor로 재시도한다.
- 상세 직접 진입은 조회 중 목록으로 보내지 않는다. 정렬·분류는 URL에서 읽어 서버 query에 전달한다.
  식당 상세 이동은 실제 서버 ID를 사용하며, 복귀 시 Query의 추가 페이지와 기존 내부 스크롤 위치를 사용한다.
- 컬렉션 목록 개수는 목록 응답의 `totalCount`, 상세 상단 `총 N곳`은 저장 식당 응답의 `totalCount`를 사용한다.
  분류·정렬 query별 첫 페이지의 전체 결과 수를 표시하며 로드된 목록 길이나 상세의 `savedCount`로 대체하지 않는다.
- 생성·더보기 동작은 후속 mutation 화면이 제공한다. 상세 관리 동작은 `owner === true`일 때만 제공받는다.
- 제품 `lazyPages`는 `SavedApiPage`, `CollectionFormQueryPage`, `CollectionEditorQueryPage`를 사용한다.
  `appRoutes`의 기존 상세 경로는 공개 조회로 열고 내 목록·생성·수정·편집의 인증 guard와 하단 내비게이션 구조는 유지한다. `index.ts`와 지도 public props는 fixture 계약을 유지한다.
- 인증 상태 전에는 보호 API를 요청하지 않는다. #221 기반의 세션별 query key와 늦은 응답 차단을 적용한다.

### Mutation 계약

| 동작           | Endpoint                                                   | 성공 후 캐시                                       | 실패 시                   |
| -------------- | ---------------------------------------------------------- | -------------------------------------------------- | ------------------------- |
| 생성           | `POST /api/v1/collections`                                 | 서버 ID로 상세 저장, 목록·대상 목록 invalidate     | 입력 유지, 중복 이름 오류 |
| 수정·공개 전환 | `PATCH /api/v1/collections/{collectionId}`                 | 상세 setQueryData, 목록·대상 목록 invalidate       | 입력·현재 상태 유지       |
| 식당 저장      | `POST /api/v1/collections/{collectionId}/restaurants`      | 상세 갱신, 관련 식당·컬렉션 목록 invalidate        | 선택 유지                 |
| 식당 해제      | `DELETE /api/v1/collections/{collectionId}/restaurants`    | 상세 갱신, 관련 식당·컬렉션 목록 invalidate        | 선택 유지                 |
| 식당 이동      | `POST /api/v1/collections/{collectionId}/restaurants/move` | 양쪽 상세 갱신, 양쪽 식당·컬렉션 목록 invalidate   | 선택 유지                 |
| 컬렉션 삭제    | `DELETE /api/v1/collections/{collectionId}`                | 삭제 리소스 cache 정리, 목록 invalidate, 목록 복귀 | 현재 화면 유지            |

- 낙관적 갱신은 추가하지 않는다. 서버 성공 이후에만 입력·선택·모달을 정리한다.
- 부분 이동 UX는 유지한다. 대상 관계를 충분히 확인하고 이동 가능한 ID만 요청한다.
  일부 페이지에 없다는 이유로 중복이 아니라고 단정하지 않는다. 동시 변경으로 409가 발생하면 실패로 처리한다.
- 이름은 서버의 앞뒤 Unicode 공백 제거·중간 공백 유지 정책을 따른다.
- 신규 설명 입력은 사용자 확정대로 공백 포함 30자, 직접 줄바꿈 금지, 붙여넣기 줄바꿈은 공백 변환이다.
- PATCH의 생략·null은 유지, 빈 설명은 삭제다. 공개 전환 성공과 링크 복사 성공은 구분한다.

### Cache·중복 확인

- 조회 3개와 write 6개의 endpoint 함수, 생성·수정·저장·해제·이동·삭제 mutation hook이 있다.
  제품 화면은 아래 조립 상태를 따르며 실서버 검증은 아직 완료되지 않았다.
- header 성공 응답을 반영하기 전에 진행 중인 동일 상세 조회를 취소해 이전 응답의 덮어쓰기를 막는다.
- 식당 관계 변경은 해당 컬렉션의 모든 정렬·분류 목록과 컬렉션/대상 목록을 갱신한다.
  이동은 양쪽 컬렉션에 적용하고, 삭제는 삭제 리소스의 조회를 취소하고 해당 cache만 정리한다.
- `getCollectionMovePlan`은 선택된 식당 ID를 기준으로 대상 컬렉션의 필요한 페이지를 조회한다.
  모든 선택 ID가 중복임을 확인한 경우에만 조기에 끝낸다. 일부 페이지 조회 실패·취소·cursor 순환은 실패로 처리한다.
- 중복 확인 결과는 쓰기 성공을 의미하지 않는다. 이후 실제 이동 요청의 409를 처리해야 하며 자동 재시도하지 않는다.
- 제품 화면은 query·mutation hook을 통해 endpoint를 호출하고 pending 중 중복 제출을 막는다.
  인증 세션 변경 시 cache 격리·늦은 mutation 응답 차단은 공통 세션 버전을 사용한다.

## 폼 제출 준비

- 사용자 확정 정책: 컬렉션명 20자·설명 30자 초과 입력을 차단하고, 어느 필드든 초과 시도 안내가 남아 있으면 생성·저장 버튼을 비활성화한다. 해당 필드를 제한 내 값으로 수정하면 초과 안내를 해제한다.

- `CollectionForm.onSubmit`은 동기 콜백 또는 `Promise<void>`를 받는다.
  응답 대기 중 입력·제출·뒤로가기를 막고, 실패하면 입력과 수정 상태를 유지해 재시도한다.
- 생성·수정 폼은 기존 컬렉션 목록을 다음 페이지까지 조회해 입력 중 앞뒤 공백을 제거한 이름으로 중복을 확인한다. 수정 대상 자신은 제외하며 목록 확인 중·실패 시 제출을 막고 조회 실패는 입력을 유지한 채 재시도한다.
- 서버 `USER-007`은 기존 이름 중복 안내에 표시한다. 다른 오류는 공통 오류 문구를 사용한다.
- `onSubmitSuccess`에서 성공 이후 복귀를 처리한다. 기존 동기 fixture의 복귀 흐름도 유지한다.
- `CollectionFormQueryPage`는 실제 생성·수정 mutation과 수정 초기값 상세 query를 사용한다.
  기존 `CollectionFormPage`는 fixture 흐름을 유지하며 제품 생성·수정 라우트는 `CollectionFormQueryPage`를 사용한다.
- 생성은 사용자가 입력한 공백을 보존해 서버 정규화에 맡긴다. 폼의 줄바꿈 방지·붙여넣기 변환·30자 제한은 유지한다.
- 수정은 초기 응답을 폼 기준값으로 고정하고 실제 변경한 필드만 PATCH한다.
  빈 설명은 `description: ''`, 변경하지 않은 필드는 생략한다. 배경 조회 성공·실패가 작성 중 입력을 초기화하지 않는다.
- 상세의 `owner === true`와 이름·색상·공개 범위를 확인한 뒤 수정 폼을 표시한다.
  생성 중복 이름은 불완전한 추가 조회 목록으로 단정하지 않고 서버 `USER-007`로 안내한다.
- 폼 오류는 인라인으로 안내하며 진단 기록은 유지하고 공통 토스트의 중복 표시는 막는다.
  성공 응답의 ID와 상세 캐시 반영 이후 원래 history·저장 대상 상태로 복귀한다.
- 2026-10-20 사용자 확인: 공백 포함 30자는 기획 요청으로 확정된 프론트 정책이다. 서버의 100자 제한은 전달·반영이 아직 되지 않은 계약 차이이며 정책 미확정 항목이 아니다.
  기존 31~100자 설명을 임의로 자르지 않고 원문을 표시하되, 폼 저장은 확정된 30자 제한을 따른다. 생성 타입·서버 제한을 프론트에서 임의 수정하지 않는다.

## 삭제·해제 확인 연결

- `CollectionDeleteQueryDialog`는 소유자 상세 조회 이후 컬렉션 삭제 또는 지정 식당 해제 mutation을 실행한다.
- 기존 `CollectionEditor`와 `CollectionConfirmDialog`를 공유해 확인창 시안·문구를 유지한다.
- 요청 중 중복 실행과 확인창 취소·Escape 닫기를 막고, 실패 시 확인창·선택·기존 데이터를 유지한다.
  오류는 공통 문구로 인라인 안내하며 진단 기록을 유지하고 토스트 중복 표시는 막는다.

- 취소 시 PATCH·복사를 하지 않는다. 공개 전환 성공 후 복사만 실패하면 공개를 유지하며 롤백하지 않는다.
- 성공 문구: `컬렉션 링크가 복사되었어요.`. 실패 문구: `링크를 복사하지 못했습니다. 다시 시도해주세요.`.
  기존 토스트 큐를 정리한 뒤 안내하며 새 재시도 버튼 없이 기존 공유 진입점을 다시 사용할 수 있다.
- 복사/공개 전환 대기 중 중복 요청을 막고 화면을 떠난 뒤 토스트나 종료 콜백을 실행하지 않는다.
- 필터별 전체 개수 응답은 위 서버 계약 반영 기준으로 연결한다. #221 기반 세션별 캐시·늦은 응답 차단은 위 Data Dependencies 기준으로 연결한다.
